# ClubOS — архитектура v0.3 (мультиклубная, MVP)

ClubOS — программа для компьютерных клубов: блокировка ПК, регистрация гостей по телефону (SMS), вход по
телефон + пароль, баланс, тарифы. Один продукт ставится в **несколько клубов** (свои и купленные другими).

Статус: **на согласование**. Что изменилось относительно v0.2 — в разделе 1.

---

## 1. Что изменилось после ответов

| Было (v0.2) | Стало (v0.3) |
|---|---|
| Один клуб | **Много клубов** в одной системе. `club_id` в каждой таблице, ПК и сотрудники привязаны к клубу |
| Вход по нику + паролю | Вход по **телефону + паролю**. Ник не нужен |
| Режим «гость за наличные» без аккаунта | **Убран.** Любой гость сначала регистрируется. Наличные принимает админ и зачисляет на аккаунт гостя |
| Только админ-ключ и ключ агента | Роли: **гость** и **сотрудник клуба**. Сотрудник входит на ПК и получает обычный рабочий стол |
| Сервер — вопрос на потом | **Один облачный сервер на все клубы** (раздел 3) |
| UTC-смещение — одна настройка на сервер | Часовой пояс **у каждого клуба** (ночной тариф зависит от местного времени) |

## 2. Роли

| Роль | Кто | Что может |
|---|---|---|
| **Платформа** | ты (вендор) | создаёт клубы, выдаёт доступ владельцу клуба. На MVP — один секретный ключ в переменной окружения |

| **Гость** (`guest`) | клиент клуба | регистрируется, входит, пополняет баланс, запускает сессию |

## 3. Общая схема и где живёт сервер

Ты не знал, что ответить про сервер, — это решение принимаю я, вот оно:

**Один сервер в интернете (облако) обслуживает все клубы.** Клубу ничего устанавливать на сервер не нужно, только клиент на ПК.

```
   КЛУБ А                              ┌───────────────────────────────────┐
 ┌──────────────┐                      │          ClubOS server            │
 │ ПК 1..N      │ ── HTTPS ──────────▶ │ FastAPI                           │
 │ клиент (C#)  │ ◀───────────────────  │                                   │
 └──────────────┘                      │ каждый запрос → «контекст клуба»: │
   КЛУБ Б                              │ ключ ПК / токен → club_id         │
 ┌──────────────┐                      │                                   │
 │ ПК 1..N      │ ── HTTPS ──────────▶ │ routers → services → БД           │
 └──────────────┘                      │ (club_id в каждой таблице)        │
 ┌──────────────┐                      └───────┬───────────────┬───────────┘
 │ веб-админка  │ ── HTTPS ──────────▶         │               │
 │ (позже)      │                              ▼               ▼
 └──────────────┘                       SMS-провайдер     платёжный
 ┌──────────────┐                       (общий, позже)     провайдер (позже)
 │ Платформа    │ ── ключ платформы ─▶
 │ (ты)         │
 └──────────────┘
```

**Почему облако, а не сервер в каждом клубе.** Ты продаёшь продукт владельцам клубов, они не админят серверы.
В облаке: обновления у всех сразу, SMS и платежи настраиваются в одном месте, ты контролируешь лицензии.

**Цена этого решения (честно):**
- Нет интернета в клубе → ПК не могут проверить состояние. Позже клиент научим доживать текущую сессию без связи; в MVP — нет.
- Ты отвечаешь за работу сервера и за данные клубов.
- Телефоны гостей — персональные данные россиян (152-ФЗ): серверы с базой должны стоять в РФ.

**Для разработки ничего не меняется:** пока сервер на твоём компьютере (`localhost`), код тот же. Выбор хостинга — позже.

## 4. Мультиклубность: правила

1. **`club_id` есть в каждой таблице** с данными клуба: ПК, тарифы, аккаунты, сессии, журнал денег, платежи, логины, аудит.
2. **Клуб определяется на сервере, а не приходит от клиента.** Запрос от ПК → ключ ПК → ПК → его клуб. Запрос сотрудника → токен → аккаунт → его клуб.
   Единственное исключение — **форма входа в админку**: там сотрудник указывает код клуба (`slug`), потому что один и тот же номер может быть
   сотрудником в нескольких клубах. Это лишь «куда входим»: пароль проверяется внутри этого клуба, а дальше клуб берётся из токена.
   В теле запроса или URL `club_id` не принимаем никогда — иначе гость клуба А подставит чужой.
3. **Все запросы к БД идут через единую зависимость «контекст клуба»**, которая добавляет `WHERE club_id = …`.
   На каждый эндпоинт — тест «клуб А не видит и не меняет данные клуба Б».
4. **Уникальность — внутри клуба:** телефон гостя `(club_id, phone)`, название ПК `(club_id, name)`.
5. **Аккаунт гостя — свой в каждом клубе.** Один человек в двух клубах = две регистрации, два баланса.
   Так деньги одного клуба никогда не оказываются услугой другого (иначе нужны взаиморасчёты между клубами).
   Единый аккаунт для твоей сети клубов — позже, как отдельная сущность «организация».
6. **Часовой пояс — настройка клуба** (`clubs.utc_offset`). `billing.py` перестаёт читать глобальный `CLUB_UTC_OFFSET`
   и получает смещение параметром.
7. **SMS платишь ты, а тратят клубы** — поэтому лимиты SMS считаем **по клубам** (суточный потолок на клуб), чтобы один клуб
   не выжег бюджет. Позже эти расходы можно перевыставлять.
8. **Платежи (позже):** у каждого клуба свой аккаунт в платёжной системе, деньги идут клубу напрямую.
   Платформа деньги гостей не принимает — так проще и юридически, и технически.

## 5. Режимы ПК

Клиент по-прежнему опрашивает сервер раз в 2–3 с. Но теперь ПК — это не «заблокирован / нет», а три режима:

```
                     вход гостя (телефон+пароль)
   ┌────────┐   ───────────────────────────────▶   ┌─────────────────────┐
   │ LOCKED │          ЛИЧНЫЙ КАБИНЕТ              │  кабинет гостя      │
   │ экран  │   (всё ещё заблокирован: баланс,     │  баланс, тарифы     │
   │ входа  │    тарифы, «пополнить»)              └──────────┬──────────┘
   └───┬────┘                                                 │ выбрал тариф
       │ ▲                                                    ▼
       │ │ сессия кончилась / стоп           ┌──────────────────────────┐
       │ └───────────────────────────────────│  GUEST_SESSION           │
       │                                     │  ПК разблокирован        │
       │ вход сотрудника (телефон+пароль)    └──────────────────────────┘
       ▼
   ┌───────────────────────────────┐   «Заблокировать» / выход
   │ STAFF_DESKTOP                 │ ────────────────────────────▶ LOCKED
   │ обычный рабочий стол,         │
   │ без тарифа и оплаты           │
   └───────────────────────────────┘
```

Режим сервер **вычисляет**, а не хранит отдельной колонкой:
1. есть активный вход сотрудника на этом ПК → `staff_desktop`;
2. иначе есть активная сессия → `guest_session`;
3. иначе → `locked` (если на ПК есть вход гостя — клиент показывает кабинет).

Ответ `GET /api/agent/state` (ПК определяется по ключу, id в URL больше нет):
```json
{ "mode": "locked | guest_session | staff_desktop",
  "club_name": "Demo Club", "pc_name": "PC-1",
  "account": { "phone_masked": "+7 *** ***-12-34", "balance": 350 },
  "session": { "tariff": "...", "seconds_left": 3600 } }
```
`club_name` и `pc_name` приходят во всех режимах: экран блокировки показывает название клуба и номер ПК, и клиенту не нужно
хранить их у себя (переименовали клуб на сервере, и надпись на экране сменилась сама).
Сотрудник на рабочем столе **не создаёт сессию и не попадает в выручку**; вход и выход записываются в журнал аудита.

## 6. Модель данных

Все таблицы, кроме `clubs`, содержат `club_id`. Колонки `id`, `created_at` не повторяю.

**clubs** — `slug` (уникальный публичный код клуба для входа в админку), `name`, `utc_offset` (часы), `status` (`active` / `suspended`), настройки: `min_topup`, `max_topup`, `idle_logout_minutes`

**pcs** (есть, дополняем) — `club_id`, `name`, **`key_hash`** (свой ключ у каждого ПК), `last_seen`; уникально `(club_id, name)`

**tariffs** (есть, дополняем) — `club_id`, остальное как сейчас

**accounts** — `club_id`, `phone` (+7XXXXXXXXXX), `password_hash`, `role` (`guest` / `staff`), `balance` (целые рубли, ≥ 0),
`status` (`active` / `blocked`), `phone_verified_at`, `failed_logins`, `locked_until`; уникально `(club_id, phone)`

**logins** — «кто сейчас вошёл куда». Токены **непрозрачные** (случайная строка, в БД — хеш), без JWT:
выход мгновенно обнуляет токен.
`club_id`, `account_id`, `pc_id` (null — вход с веб-админки), `token_hash`, `last_seen_at`, `expires_at`, `ended_at`.
На одном ПК одновременно не больше одного активного входа.

**phone_verifications** — `club_id`, `phone`, `purpose` (`register` / `reset`), `code_hash`, `expires_at` (+5 мин),
`attempts` (макс. 5), `consumed_at`, `ip`, `pc_id`. Лимиты на SMS считаем по этой же таблице — Redis не нужен.

**wallet_transactions** — журнал денег, только добавление: `account_id`, `amount` (±), `balance_after`,
`kind` (`topup_cash` · `topup_online` · `session_charge` · `adjustment`), `session_id?`, `payment_id?`, `staff_id?`, `comment`.
`accounts.balance` — кэш суммы журнала; проверка в тестах: `SUM(amount) == balance`.

**sessions** (есть, дополняем) — `club_id`, **`account_id` обязателен**, остальное как сейчас

**payments** (этап с платежами) — `club_id`, `account_id`, `amount`, `provider`, `provider_payment_id` (уникальный), `status`, `paid_at`

**audit_log** — `club_id`, `actor_account_id`, `pc_id`, `action` (`staff_unlock`, `staff_lock`, `topup_cash`, `account_block`, …), `details`, `ip`

## 7. Ключевые потоки

### 7.1 Регистрация гостя (на экране ПК)

```
POST /api/auth/register/request-code {phone}          (ключ ПК → клуб)
   → нормализуем номер → проверяем лимиты → код 6 цифр → phone_verifications → SMS
POST /api/auth/register/confirm {phone, code, password}
   → код верен, не просрочен, попыток < 5 → создаём account(role=guest, phone_verified_at=now) → токен
```
- SMS: не чаще 1 в 60 с на номер, до 5 в час на номер, до 20 в час с одного ПК и **суточный потолок на клуб**.
  Лимита «по IP» нет сознательно: сервер в облаке видит у всех ПК клуба один внешний адрес (NAT), и такой лимит заблокировал бы весь клуб.
- Номер уже зарегистрирован в этом клубе — отвечаем так же, как для нового, SMS не шлём (не раскрываем базу).
- 5 неверных попыток — код сгорает.
- В MVP «отправка SMS» = печать кода в консоль сервера. Реальный провайдер подключается заменой одного файла.
- Сброс пароля — тот же механизм (`purpose = reset`).

### 7.2 Вход

`POST /api/auth/login {phone, password}` с ключом ПК. Ответ — токен.
- Ищем аккаунт по `(club_id ПК, phone)`. Ошибка всегда одинаковая: «неверный номер или пароль».
- 5 неудач подряд → блокировка на 15 минут (`locked_until`).
- `role = staff` → режим `staff_desktop` + запись в аудит.
- `role = guest` → кабинет. Один гость — одна активная сессия, вход на втором ПК не даст стартовать вторую сессию.
- Бездействие в кабинете без сессии `idle_logout_minutes` → автоматический выход.

### 7.3 Списание (стыкуется с `billing.py`)

| Тариф | Когда списываем | Если денег мало |
|---|---|---|
| `package` | при старте, вся цена | старт запрещён (402, «не хватает N ₽») |
| `night` | при старте, вся цена | старт запрещён; окно ночи считается по часовому поясу клуба |
| `hourly` | при закрытии, по фактическим минутам | `planned_end = старт + баланс / цена × 60`; кончились деньги → сессия закрывается как истёкшая |

Для почасового `planned_end` пересчитывается при каждом пополнении, поэтому гость может пополнить баланс во время игры
и время продлится. Существующие `close_expired()` / `is_expired()` работают без изменений.
Гость при этом остаётся в кабинете: ПК заблокирован, но он может пополнить баланс и стартовать заново.
Возвратов нет (пакет сгорает при досрочном стопе), как и сейчас.

### 7.4 Пополнение

- **MVP:** сотрудник принимает наличные и делает `POST /api/admin/accounts/{id}/topup {amount}` → `wallet.apply(kind=topup_cash)` + аудит.
  Поиск гостя — по номеру телефона.
- **Пополнение по номеру ПК** (11.10.2026): `GET /api/admin/pcs/{id}/guest` говорит, кто сейчас за ПК (идёт сессия или гость вошёл в кабинет) и сколько у него на балансе, `POST /api/admin/pcs/{id}/topup {amount, comment}` зачисляет наличные именно ему (тот же `cashier.change_balance`: баланс, журнал, аудит; комментарий по умолчанию «Пополнение за PC-1»). Нет гостя за ПК: 409 с подсказкой искать в «Гостях». Кнопка «Пополнить баланс» стоит в панели ПК на карте клуба и рядом с каждым вызовом администратора в «Заказах».
- **Самостоятельное онлайн-пополнение** (QR/СБП или карта): платёжного провайдера пока нет, поэтому сначала делаем
  интерфейс `PaymentProvider` и заглушку для разработки, потом подключаем реального.
  Правила на будущее: зачисляет только webhook провайдера (не клиент), идемпотентность по `provider_payment_id`,
  сумма берётся из ответа провайдера.

### 7.5 Создание клуба (платформа)

`POST /api/platform/clubs {slug, name, utc_offset, owner_phone, owner_password}` с ключом платформы →
создаётся клуб и первый staff-аккаунт. Дальше сотрудник сам создаёт ПК и тарифы; **ключ ПК показывается один раз**
при создании (в БД только хеш) и прописывается в клиент на этом ПК.

## 8. Безопасность

**Самая опасная функция продукта — вход сотрудника на рабочий стол.** Кто получил staff-пароль, получил бесплатный доступ ко всем ПК клуба. Поэтому:
- Staff-аккаунты создаются только платформой или сотрудником того же клуба, не саморегистрацией.
- Staff-вход — только с ПК этого клуба (по ключу ПК) и с блокировкой после неудачных попыток, как у гостей.
- Каждый staff-вход и выход пишется в `audit_log` (кто, на каком ПК, когда).
- Минимальная длина staff-пароля больше, чем у гостя (например 10 против 8).
- Админ клуба может принудительно «заблокировать ПК» из админки (завершает staff-вход).

**Про «один общий аккаунт для админов во всех клубах».** Для твоей собственной сети — удобно. Но если продаёшь другим, один общий логин на все клубы-покупатели — это универсальная отмычка: утечка одного пароля открывает рабочие столы у всех клиентов.
Поэтому в схеме staff-аккаунты **привязаны к клубу**; в твоей сети можно завести в каждом клубе один и тот же номер и пароль — это те же удобства без общего риска.
Общий для админов клуба аккаунт тоже допустим (так работают многие клубы), но тогда в аудите будет видно «staff клуба», а не конкретного человека.

Остальное:
- **Ключ ПК лежит на ПК гостя**, гость может его вытащить. Поэтому ключ даёт только «я ПК №N» (состояние, регистрация, вход); все остальные действия требуют токена аккаунта. Баланс, время и разблокировку решает только сервер.
- **Пароли** — argon2id, минимум 8 символов. Коды SMS и пароли хранятся только хешами и не попадают в логи; номера в логах маскируются.
- **Деньги:** баланс не может быть < 0 (CHECK в БД); изменяется только через `wallet.apply` внутри транзакции с записью в журнал;
  на PostgreSQL — блокировка строки аккаунта (`SELECT … FOR UPDATE`).
- **HTTPS** обязателен, как только сервер выходит за пределы localhost.
- Заблокированный клуб (`suspended`) — все его ПК получают `locked`, staff-вход тоже отключается (на случай неоплаты лицензии).

### Клиент на ПК: две части (идея из изучения open source, код оттуда не берём)

Просмотр открытых проектов (раздел «Что нашли в open source» ниже) дал одну полезную идею для клиента на Windows:
- **Служба Windows** (запускается от системы, раньше всех, перезапускается при падении): держит связь с сервером, опрашивает состояние, выполняет команды.
- **Оверлей WPF** (запускается в сессии пользователя): рисует полноэкранный экран блокировки, формы входа и регистрации, меню гостя.
- Они общаются через **Named Pipe** (локальный канал). Причина разделения: служба Windows по правилам системы не может показывать окна
  на рабочем столе пользователя, а окно оверлея не должно быть единственным, что стоит между гостем и рабочим столом.

На сервер это влияет мало: контракт `GET /api/agent/state` и вход гостя остаются теми же. Позже добавим удалённые команды
(перезагрузка / выключение ПК из админки) и метрики ПК (загрузка CPU/RAM) в heartbeat — они были в изученном Cafe-OS.

**Статус: реализовано** (папка `client/`, подробности и инструкция по установке — [client/README.md](client/README.md)).
Решения, принятые при реализации:
- **Ключ ПК и токен гостя живут только в службе.** Оверлей работает в сессии гостя (недоверенная среда) и по каналу может попросить
  лишь одну из 12 разрешённых операций; ни ключа, ни токена, ни произвольного запроса к серверу у него нет. Токен лежит в файле, зашифрованном
  DPAPI, в папке с правами только для системы и администраторов, и переживает перезапуск службы.
- **Если токен потерян, а сервер считает гостя вошедшим, кабинет не показывается:** гость видит обычный вход и входит заново (сервер это разрешает).
- **Без связи:** после загрузки ПК закрыт; играющий гость играет до 2 минут запаса или до конца оплаченного времени; сотрудник остаётся
  на рабочем столе; закрытый ПК остаётся закрытым.
- **Киоск включается только флагом `--kiosk`;** по умолчанию оверлей — обычное окно, чтобы разработка не блокировала компьютер.
  Перехват клавиш работает только пока виден экран блокировки.
- **Тест «живьём»** (Python-сервер + служба + оверлей, кнопки нажимались через интерфейс): регистрация по SMS, вход, пополнение, старт и остановка
  сессии, перезапуск службы, вход сотрудника, принудительная блокировка, киоск на весь экран. Найденные при этом ошибки (перерисовка списка тарифов
  каждую секунду, потеря входа при перезапуске службы, окно слушателей канала) исправлены и покрыты тестами.
- Не проверено на настоящих клубных ПК: установочные скрипты проверены только на синтаксис, служба запускалась как консольная программа.

## 11. MVP: что входит и в каком порядке

**Входит:**
1. ✅ **Готово.** Alembic; разнос `main.py` на роутеры и сервисы.
2. ✅ **Готово.** Клубы: `club_id` везде, ключ на каждый ПК, «контекст клуба», создание клуба платформой, часовой пояс клуба, тесты на изоляцию клубов.
   Сюда же вошли аккаунты сотрудников и вход в админку по телефону и паролю (без них нечем авторизовать админские запросы клуба):
   argon2, блокировка после 5 неудач, токены с хранением хеша, выход. Единственное, что осталось от «гостевой» части, — таблица `accounts` с ролью `guest`.
3. ✅ **Готово.** Гости: регистрация по телефону (SMS-заглушка в консоль), вход телефон+пароль на ПК, сброс пароля.
   Коды SMS хранятся хешем, живут 5 минут, 5 попыток, лимиты на номер/ПК/клуб; ответы не выдают, какие номера зарегистрированы.
4. ✅ **Готово.** Режимы ПК: таблица `logins` с правилом «один вход на ПК», `/api/agent/state` с тремя режимами,
   вход сотрудника → рабочий стол, выход гостя по бездействию, принудительная блокировка ПК, аудит.
5. ✅ **Готово.** Баланс: `wallet` + журнал, пополнение наличными и ручная корректировка сотрудником, блокировка гостя,
   старт/стоп сессии гостем с баланса, почасовой тариф с продлением при пополнении.
6. ✅ **Готово.** `fake_agent.py` 2.0 и сквозной тест (`tests/test_e2e.py`): платформа создаёт клуб → сотрудник создаёт ПК и тариф →
   гость регистрируется и входит → сотрудник пополняет → гость стартует и останавливает → рабочий стол сотрудника → выручка в отчёте.

**Результат MVP (сервер):** достигнут — весь сервер проверяется через `/docs` и `fake_agent.py`, без внешних сервисов (134 автотеста).

### Решения, принятые по ходу реализации
- **Токены привязаны к назначению.** Токен, выданный на ПК (гость или сотрудник), не открывает админку; токен гостя работает только вместе
  с ключом того ПК, где его выдали. ПК — недоверенная среда, токен оттуда не должен давать управление клубом.
- **Пароль сотрудника по SMS не сбрасывается** (перехват SIM-карты дал бы доступ к рабочим столам). Его меняет платформа:
  `POST /api/platform/clubs/{id}/reset-staff-password`. У гостей сброс по SMS работает.
- **Выход гостя во время сессии запрещён** (409): сначала «завершить сессию», чтобы деньги не пропадали незаметно.
- **Стоимость почасового тарифа считается целыми числами** (микросекунды). Расчёт через float давал 32 ₽ при балансе 31 ₽ на «круглых» границах
  (находка при проверке; закрыто тестом).
- **Выручка в отчёте** считается по закрытым сессиям (пакет/ночь попадают в день закрытия, а не оплаты). Для кассового отчёта по дням
  позже добавим отчёт по журналу денег.
- **Тесты ускорены** облегчёнными параметрами argon2 только в тестовом окружении; в проде остаются стойкие.
- **Доплата по часам после пакета или ночи.** Когда оплаченный тариф кончился, а у гостя на балансе есть деньги, сессия не закрывается,
  а идёт дальше по почасовой ставке клуба (цена самого дешёвого действующего почасового тарифа; 120 ₽/ч = 2 ₽ в минуту).
  Ставка запоминается в сессии при старте (`sessions.overtime_price`), конец тарифа тоже (`sessions.base_end`). Как и у почасового тарифа,
  деньги списываются при закрытии за фактически сыгранное время (не больше баланса, ни рубля сверх), а `planned_end` = конец тарифа +
  время, на которое хватает баланса; пополнение продлевает игру. В `seconds_left` до конца тарифа идёт время тарифа, после него время на балансе.
  Если на балансе после покупки пакета нет денег, сессия кончается ровно вместе с пакетом, поэтому пополнять нужно заранее.
  Если в клубе нет почасового тарифа, доплаты нет. В журнале денег доплата отдельной записью с комментарием.
- **Предупреждения о конце времени** (клиент): короткое окно в правом нижнем углу поверх всех окон со звуком за 15, 10 и 5 минут
  (`SessionWarnings`, `ToastWindow`). Окно не забирает фокус у игры и гаснет само. Текст зависит от случая: тариф кончится и дальше
  почасовая оплата; сессия кончится, пополните баланс; баланс кончается. Плавающего таймера в игре нет: время видно в меню.
  Поверх игры в «настоящем» полноэкранном режиме Windows такие окна не показывает, там нужен режим «в окне без рамки».
- **Очистка ПК после сессии (сделано).** Когда сессия гостя кончилась (остановил сам, вышло время или деньги, пропала связь), служба
  (под системой, гость остановить её не может) закрывает всё, что гость запустил, и убирает его данные; оверлей очищает буфер обмена.
  - *Кого чистим.* Только сессию Windows-пользователя из `guest_user` (agent.json). Если в консоли вошёл кто-то другой (администратор),
    очистка не делает ничего. Без `guest_user` она тоже выключена. Режимы `cleanup`: `off`, `dry-run` (только пишет в журнал, что сделала бы;
    по умолчанию), `on` (скрипт установки ставит его).
  - *Какие процессы.* Служба делает «снимок» процессов, когда ПК чистый (после включения, после ухода сотрудника, после предыдущей очистки).
    Закрываются процессы сессии гостя, которых в снимке не было: игры, лаунчеры, браузеры, значки в трее. Системные (explorer, dwm, svchost и
    подобные) и сам ClubOS не закрываются никогда; свои исключения добавляются в `cleanup_keep`. Если снимка нет (служба перезапустилась посреди дня),
    закрываются только известные программы гостей (Steam, браузеры, Discord и т. п.). Лаунчеры, которые перезапускают друг друга, добиваются за три прохода.
  - *Какие данные.* Внутри профиля гостя: профили Chrome, Edge, Firefox, Яндекс, Brave, Opera; Discord, Telegram, Epic, Battle.net, Riot, Ubisoft;
    вход в Steam (автовход и `loginusers.vdf`); Загрузки, Документы, Изображения, Видео, Музыка, Недавние, Temp; на рабочем столе всё, кроме ярлыков.
    Свои папки добавляются в `cleanup_paths` (путь от профиля). Выйти за пределы профиля нельзя (проверяются `..`, абсолютные и сетевые пути),
    профиль обязан лежать прямо в `C:\Users`, ссылки и точки соединения удаляются сами, а то, на что они указывают, не трогается.
  - *Что не делается.* Полный сброс настроек Windows и профиля (обои, ассоциации файлов, установленные гостем программы). Для этого нужен либо
    профиль гостя из шаблона, который пересоздаётся при выходе, либо заморозка диска (Deep Freeze и подобные). Очистка ClubOS их не заменяет, а дополняет.

### Веб-админка (v0.5) — сделана
Лежит прямо в сервере (`/admin/`, файлы в `app/web/admin/`): без сборки, без внешних библиотек и без интернета, работает в локальной сети клуба.
Разделы: компьютеры (живая сетка), гости, сессии, тарифы, отчёт за смену, журнал действий. Решения:
- **Безопасность по построению:** страница создаётся только текстовыми узлами, вставки HTML в коде нет (тест это проверяет); сервер отдаёт CSP
  «только с себя» (проверено в настоящем браузере: встроенный и внешний скрипт и обращение наружу блокируются), запрет показа во фрейме,
  `no-store` для API. Токен — в `sessionStorage`.
- **Время клуба, а не браузера:** все даты показываются и вводятся по `clubs.utc_offset`; границы «сегодня/вчера» считаются по полуночи клуба.
- **Поиск гостя по части номера** (от 3 цифр) — кассир на стойке не вводит номер целиком.
- **Отчёт за смену** (`GET /api/admin/report/summary`): выручка и сессии по тарифам, наличные по каждому кассиру (для сдачи кассы), корректировки отдельно.
- Проверено живьём в браузере: вход, сетка ПК, запуск и остановка сессии, пополнение, поиск, отчёт, журнал, вид на телефоне, атака через название ПК.
- Не вошло: управление сотрудниками и роли (кассир/админ), правка тарифов (можно отключить и создать заново), переименование и удаление ПК,
  обновление «по событию» вместо опроса раз в 3 секунды (WebSocket).

## 12. Допущения (скажи, если не так)

1. Гость регистрируется отдельно в каждом клубе, баланс не переносится между клубами.

## 14. Следующая версия: меню гостя, сервисы, карта клуба

Описание от заказчика (по двум референсам: экран гостя на ПК и админка с картой клуба). Гость выбирает свободный ПК у администратора, садится,
входит в аккаунт и попадает в **меню**: игры и приложения, вызов администратора, заказ еды и напитков к столу, оплата с баланса или по QR.

### Что уже есть и что нужно добавить

| Часть | Уже есть | Нужно |
|---|---|---|
| Меню гостя (клиент) | вход, регистрация, кабинет с балансом и тарифами, таймер сессии (сделано в первой версии меню) | окно-меню с вкладками «Библиотека» (сверху игры плакатами с обложками, ниже под линией программы), «Бар», «Тарифы» (во время сессии «Продление»), поиск, запуск; справа колонка: сколько осталось времени, баланс, «Продлить тариф», «Пополнить баланс», «Вызвать администратора», «Завершить сессию» |

### Решения по построению

- **Каталог игр хранит сервер** (таблица `apps`: название, вкладка, категория, возрастной ценз, путь к exe, вкл/выкл; картинка обложки лежит отдельно в `app_covers`, см. «Обложки игр»). Клиент запускает только
  записи из каталога по номеру, гость путь не вводит и аргументов не передаёт. Путь проверяется на ПК: абсолютный, файл существует, расширение `.exe`.
  Если игры на этом ПК нет, карточка серая с подписью «Не установлена».
- **Меню остаётся обычным окном на время сессии.** Игра запускается из меню, окно сворачивается; вернуться можно кнопкой в панели задач. Отдельного плавающего таймера нет: время и баланс видны в самом меню. Менять оболочку Windows не нужно.
- **Вызов и заказ идут через сервер**, а не напрямую администратору: таблицы `calls` и `orders` (+ `order_items`), статусы `new → accepted → done / cancelled`,
  у каждого есть `club_id` и `pc_id`, поэтому «за какой стол» известно по построению. Администратор видит их в админке со счётчиком в шапке.
- **Деньги за заказ списываются только через `services/wallet.py`** (новый вид операции `shop_purchase`). Отмена заказа до выдачи возвращает деньги
  отдельной операцией, а не правкой старой записи. Склад (остатки) пока опционален: товар можно просто скрыть.
- **Статусы ПК для карты** добавляем к текущим (`offline`, `locked`, `guest_session`, `staff_desktop`): «забронирован», «обслуживание», «нет связи»,
  «заблокирован». Расстановка хранится на сервере (`pcs.zone`, `pcs.pos_x`, `pcs.pos_y`), редактируется в админке перетаскиванием.
- **Железо ПК** (процессор, память, видеокарта, диски, сеть) присылает служба клиента раз в сутки и при смене конфигурации; в карте видно «изменена конфигурация».
- **Оформление** в цветах «чёрный, белый, золото» (было чёрный и красный, сменили 11.10.2026): чёрный и белый главные (фон, текст, главные кнопки белые с чёрным текстом), золото только для мелких деталей (полоски, подписи, рамки при наведении и в фокусе, значки). Красный остался только для ошибок и опасных действий, зелёный и оранжевый для состояний. Шрифт Manrope вместо Bahnschrift (11.10.2026: узкие заглавные буквы казались слишком крупными): он вшит в клиент, а не берётся из Windows; заголовки обычным регистром; значки Phosphor. Вход гостя по центру окна отдельной рамкой, вкладки меню в выезжающей слева панели. Админка клуба и панель платформы переведены на тот же вид (шрифт `app/web/admin/fonts`, значки `icons.js` в меню, вход рамкой по центру); сторонние шрифт и значки перечислены в THIRD-PARTY.md. Берём из референсов раскладку и состав экранов, а не их картинку: это чужой коммерческий продукт,
  а свой продукт должен выглядеть как свой.

### Бар и вызов администратора (сделано)

- **Данные.** `products` (меню клуба), `orders` + `order_items` (название и цена копируются в заказ, правка меню старые заказы не меняет),
  `calls` (вызовы; на одном ПК не больше одного открытого, это закреплено частичным уникальным индексом).
- **Деньги.** Заказ списывается с баланса сразу (`shop_purchase`), отмена до выдачи возвращает всю сумму отдельной записью (`shop_refund`).
  Смена статуса идёт условным UPDATE, поэтому два одновременных «отменить» не вернут деньги дважды. Цену сервер берёт из меню, из запроса не верит.
  Защита от спама: не больше 5 заказов в работе у одного гостя, не больше 20 штук одного товара, не больше 20 строк в заказе.
- **Статусы.** `new` (ждёт) → `accepted` (готовится) → `done` (выдан); отмена из `new` и `accepted`. Гость может отменить сам, пока заказ `new`.
  Что осталось в работе, сотрудник видит в разделе «Заказы» (старые сверху), с названием ПК и номером гостя; значок со счётчиком на вкладке
  и короткий сигнал при новом заказе или вызове (админка опрашивает `/api/admin/inbox` раз в 5 секунд).
- **Гость на ПК.** Вкладка «Бар»: меню по категориям с поиском, корзина, «Заказать», «Мои заказы» со статусами, «Вызвать администратора»
  (на любой вкладке; после «Подошёл» у сотрудника надпись у гостя меняется сама). Корзина, заказы и вызов очищаются, когда гость выходит.
- **Оплата по QR** пока не сделана: нужен платёжный провайдер. Сейчас платёж только с баланса.
- **Отчёт за смену** показывает сумму продаж бара отдельно от выручки за игру (`shop_revenue`, `shop_orders`; отменённые не считаются).
- **Меню бара и каталог игр** кладутся в клуб командой `python -m scripts.seed_catalog <код клуба>`.

### Карта клуба, дашборд, железо ПК (сделано)

- **Админка с меню слева**: Дашборд, Карта клуба, Гости, Сессии, Бронирование, Заказы, Тарифы, Игры, Бар, Реклама, Отчёт, Журнал. Отдельной вкладки «Компьютеры» нет (11.10.2026 убрали как дубль): всё про ПК делается на карте клуба, в панели выбранного ПК (старая ссылка `#/pcs` ведёт на карту).
- **Карта клуба.** У ПК есть зал (`pcs.zone`) и клетка на сетке 30 x 20 (`pos_x`, `pos_y`), одна клетка на один ПК внутри зала. «Расставить ПК»
  включает перетаскивание: ПК переносится в клетку, из «Не размещены» и обратно, при броске на занятую клетку ПК меняются местами. Расстановка
  сохраняется целиком одним запросом (`POST /api/admin/pcs/layout`): при конфликте не сохраняется ничего. Фильтры по статусам с числами,
  подсказка при наведении, боковая панель ПК: гость и тариф, остановить сессию, заблокировать, обслуживание, название и заметка, железо.
  Статусы: свободен, играет, сотрудник, нет связи, обслуживание, плюс метка «изменена конфигурация».
- **Обслуживание.** Флаг `pcs.maintenance`: гостей на такой ПК не пускают (вход, регистрация, старт сессии дают 409), сотрудник входит как обычно,
  на экране блокировки в состоянии приходит «ПК на обслуживании». Поставить флаг на ПК с идущей сессией нельзя.
- **Железо.** Служба на ПК собирает процессор, память, видеокарту, систему, диски, адрес и MAC средствами Windows (реестр, диски, сетевые адаптеры, без
  лишних библиотек) и присылает через минуту после запуска и затем раз в 6 часов (`POST /api/agent/hardware`, только ключ ПК). Если изменились
  процессор, память, видеокарта или состав дисков, ПК помечается «изменена конфигурация» до тех пор, пока сотрудник не нажмёт «Всё верно»;
  свободное место, адрес и версия системы за изменение не считаются. Первый отчёт не помечается.
- **Дашборд** (`GET /api/admin/dashboard`): загрузка зала, выручка за игру, бар, принято наличными, новые гости, очередь заказов и вызовов; сутки по времени клуба.

### Бронирование (сделано)

- **Модель.** `bookings`: ПК, телефон гостя, имя, комментарий, начало и конец (UTC), статус `active` / `used` / `cancelled`. Бронь делает сотрудник
  (вкладка «Бронирование»): гость называет администратору номер и время. Пересекающиеся брони одного ПК не принимаются, впритык можно.
  Начало не раньше «пять минут назад» и не дальше 30 дней вперёд, длительность от 15 минут до 12 часов. ПК на обслуживании бронировать нельзя.
- **Удержание ПК.** Бронь держит ПК за гостем с таким номером с «за 30 минут до начала» до «15 минут после начала» (но не дольше конца брони).
  В это окно чужая сессия на ПК не стартует (409 «ПК забронирован на 19:30»), а гость с этим номером стартует как обычно, и бронь становится `used`.
  Не пришёл за 15 минут: ПК освобождается сам, бронь остаётся в списке с пометкой «не пришёл». Величины настраиваются в `app/config.py`
  (`BOOKING_LEAD_MINUTES`, `BOOKING_GRACE_MINUTES`).
- **Правка брони** (11.10.2026): `PATCH /api/admin/bookings/{id}` меняет любую часть действующей брони: время начала и длительность (гость позвонил, что не успевает; сдвигается и «не пришёл»), ПК, номер, имя, комментарий (гость просит мышь или клавиатуру). Проверки те же, что при создании (не в прошлом, не дальше 30 дней, ПК не на обслуживании, пересечения с другими бронями, сама с собой бронь не пересекается); закрытую бронь (гость пришёл, отменена) менять нельзя. Журнал: «Бронь изменена» со списком полей. В списке броней отдельный столбец «Комментарий» и кнопки «Комментарий» (быстрая заметка), «Изменить» (всё остальное, быстрые сдвиги +15 мин, +30 мин, +1 ч, +2 ч), «Отменить»; комментарий виден и на карте клуба.
- **Админка.** Список будущих броней и история, отмена; на карте клуба ПК с действующей бронью показывается как «Бронь 19:30», в карточке
  на карте клуба тоже подпись.
- **Не вошло.** Бронь самим гостем с ПК или с телефона (нужна авторизация по SMS вне клуба), предоплата брони, напоминание гостю.

### Выбор программы на ПК (сделано)

- **Зачем.** Администратор добавляет в меню гостя программу (TeamSpeak, Discord, браузер) и не хочет набирать путь к exe руками. Из браузера полный путь к файлу
  не узнать (браузер отдаёт только имя), поэтому список приходит от самого ПК клуба, и выбранный путь заведомо существует там, где программу будут запускать.
- **Клиент.** Служба (`ProgramsReporter`, `InstalledPrograms`) собирает ярлыки `.lnk` из общего меню «Пуск», из меню «Пуск» и с рабочего стола каждого
  пользователя Windows (так находятся и программы, поставленные «только для меня», вроде `AppData\Local\Programs`), раскрывает их в путь к exe через COM
  `WScript.Shell` и оставляет настоящие программы: без удаления, справки, установщиков и обновлялок, без системных папок, без несуществующих файлов, один путь один раз,
  не больше 600. Список уходит на `POST /api/agent/programs` при запуске службы (через 45 секунд), затем раз в 2 часа только если он изменился, и сразу,
  когда администратор нажал «Обновить список»: сервер тогда добавляет в ответ `state` признак `scan_programs`.
- **Иконки.** Вместе с программой служба берёт её иконку так, как показывает Windows (`ShellProgramIcons`, интерфейс `IShellItemImageFactory`, отдельный поток STA): PNG 96 x 96
  (если больше 28 КБ, то 64 x 64), без внешних библиотек (PNG собирает `PngEncoder`). Иконка уходит в том же запросе полем `icon` (base64). Нет иконки у файла, получить её не вышло:
  программа остаётся без неё, список не страдает. Сменилась иконка (обновилась программа): список отправляется заново.
- **Сервер.** У ПК три поля (миграция 0012): `programs_json`, `programs_at`, `programs_wanted_at`. Принимаются только пути той же формы, что и при ручном вводе
  (`check_launch_target`: диск, обратные слэши, без `..`, оканчивается на `.exe`), названия в одну строку, не больше 800. `GET /api/admin/pcs/{id}/programs` отдаёт список,
  время отчёта и признак «ждём ответ ПК»; `POST /api/admin/pcs/{id}/programs/rescan` просит обновить. Чужой клуб: 404. Иконка принимается, только если это настоящий PNG
  размером от 48 до 256 пикселей (меньше обложкой не станет) и до 30 КБ (иначе выбрасывается одна иконка, программа остаётся); всех иконок вместе на ПК не больше примерно 3 МБ. `?icons=false` отдаёт лёгкий список
  (у программы только флаг `has_icon`) для частого опроса, пока ждём ответ ПК.
- **Админка.** В окне «Новая игра» при способе «Файл на ПК» рядом с путём кнопка «Выбрать на ПК»: окно со списком программ выбранного ПК, поиск по названию, «Обновить список»
  (ждёт ответ ПК до 30 секунд), у каждой программы её иконка. Выбор подставляет путь и, если название пустое, название программы.
- **Иконка в меню гостя ставится сервером сама** (`covers.fill_from_programs`, источник обложки `program`, миграция 0013): записи вкладки «Программы» со способом «Файл на ПК» и без картинки
  берут иконку той программы, чей путь к exe совпал (без учёта регистра) в списке любого ПК этого клуба (при нескольких берётся самый свежий отчёт). Срабатывает, когда запись создают или
  правят, и когда любой ПК присылает список, поэтому программы, добавленные раньше, получают иконки без всякого повторного выбора. Ручная картинка (`manual`) главнее и не заменяется.
  Сменили путь или вкладку: иконка прежней программы снимается и берётся новая, если путь известен. У игр и записей Steam иконка не ставится: там нужен вертикальный постер.
  Плитка программы в меню гостя показывает иконку вместо буквы (картинка целиком, без обрезки); без иконки остаётся буква.
- **Что важно знать.** Путь одинаков для всех ПК клуба. Программа, поставленная в профиль одного пользователя (`C:\Users\имя\AppData\...`), у гостей под другим пользователем Windows
  не найдётся: ставьте для всех пользователей (`Program Files`).

### Реклама партнёров: заставка с баннерами на весь экран (сделано)

- **Кто что делает.** Рекламодатель присылает владельцу платформы готовый баннер. Владелец загружает его в своей панели (`/platform/`, вход по
  ключу платформы): картинка PNG или JPEG до 2 МБ, название (видно только владельцу), рекламодатель, erid (маркировка), сколько секунд показывать,
  окно показа от и до, порядок в очереди. Баннеры общие для всех клубов (в таблице `ads` нет `club_id`). Клуб сам включает показ у себя на вкладке
  «Реклама» в админке (`clubs.ads_enabled`, по умолчанию выключено) и видит свою долю дохода (`clubs.ads_club_share`, по умолчанию 30%); долю задаёт
  только платформа. Платформа тоже может включить или выключить рекламу клубу. Баннер без картинки не показывается. Одновременно в очереди не больше 12.
- **Хранение картинок.** Таблица `ad_images` (миграция 0009): байты, тип, размеры, отпечаток `version` (первые 16 знаков SHA-256). Тип и размеры
  определяются по самим байтам, а не по заголовку от браузера: принимаются только PNG и JPEG, до 2 МБ, стороны от 100 до 4096. Сервер отдаёт
  картинку ПК по `GET /api/agent/ads/{id}/image` (ключ ПК; только если баннер сейчас идёт в этом клубе; кэшируется по ETag), владельцу по
  `GET /api/platform/ads/{id}/image`. Панель платформы показывает превью через `data:`-адреса: политика безопасности страницы других источников
  картинок не разрешает.
- **Как картинка попадает на ПК.** Оверлей работает от имени гостя и ключа ПК не знает, поэтому картинки скачивает служба (`AdImageCache`): берёт
  список (`GET /api/agent/ads`), качает недостающие, проверяет (PNG или JPEG по первым байтам, не больше 2 МБ, SHA-256 совпал с отпечатком из списка)
  и кладёт в папку `C:\ProgramData\ClubOS\ads` (в разработке переменная `CLUBOS_ADS_DIR`) файлом «номер-отпечаток.расширение». Служба пишет, остальные
  только читают (права выставляются, когда служба запущена от системы). Лишние файлы удаляются: выключили рекламу или заменили картинку, и на ПК остаётся
  только нужное; чужие файлы в папке не трогаются. По каналу оверлею идут только пути к файлам (картинки в строку канала не влезают). Оверлей
  дополнительно проверяет, что путь внутри папки баннеров, а расширение png/jpg. Скачивание идёт мимо общей очереди действий службы: вход гостя
  не ждёт картинки. Не успел скачаться за 6 секунд, баннер придёт без пути, и оверлей спросит ещё раз через 5 секунд.
- **Где видно гостю: заставка.** Пока за ПК никого нет, на весь экран идёт рекламный баннер (так сделано у Colizeum). Гость садится и нажимает кнопку
  мыши или клавишу (или заметно двигает мышь, от 30 пикселей: дрожь на столе не считается), и вместо баннера появляется форма входа с курсором в поле телефона;
  нажатие, разбудившее заставку, дальше не идёт (клик не попадает в форму под баннером). Гость ушёл: на пустой форме входа через 45 секунд тишины заставка
  возвращается; если что-то введено (регистрация, код из SMS), через 3 минуты, и введённое стирается, следующий гость его не увидит. ПК освободился
  (гость вышел, сессия кончилась, ПК загрузился): заставка сразу, если последние секунды никто ничего не трогал. Без рекламы или пока баннеры не скачаны
  заставки нет, показывается форма входа, как раньше. В кабинете гостя, во время игры и на рабочем столе сотрудника заставки нет (`AttractModel`).
  Баннер помещается в экран целиком по центру. Лучше всего подходит картинка 16 на 9 (1920 x 1080): она занимает весь экран. Картинка другой формы
  (обычные баннеры 2,4 к 1 или 2,8 к 1) встаёт по ширине или по высоте, а свободные поля закрашиваются продолжением её края: крайний ряд пикселей
  растягивается в сторону, поэтому баннер со сплошным или плавным фоном выглядит продолженным на весь экран без шва. Если на краю виден предмет, текст или
  фото (резкий скачок цвета между соседними пикселями, или прозрачный край), растяжка не применяется и поля остаются тёмными (`BannerEdges`). Подпись
  «РЕКЛАМА», рекламодатель и erid лежит на баннере тёмной плашкой слева внизу, по центру внизу точки карусели (текущий баннер золотой), справа внизу подсказка
  «Нажмите любую кнопку, чтобы войти». Если баннеров несколько, они сменяют друг друга по кругу, каждый столько секунд, сколько задано (от 3 до 120), смена
  плавная (0,7 с). Форма входа возвращена в прежний вид: справа на всю высоту, а название клуба, статус «ПК ЗАБЛОКИРОВАН» и номер ПК слева сверху; при нехватке
  высоты форма не прокручивается, а уменьшается целиком. Клиент спрашивает службу о списке раз в минуту; при сбое остаются прежние баннеры; картинку,
  которую не удалось открыть, оверлей убирает из очереди до новой версии. Градиентов в оформлении нет: на части видеокарт они дают белые полосы.
- **Учёт показов.** Считает сервер по опросам ПК (`/api/agent/state`), но только пока заставка действительно на экране. Оверлей сообщает службе (`ads.visible`, раз в
  5 секунд и при каждой смене), служба добавляет это к опросу параметром `ads=1` (заставка) или `ads=0` (гость у формы входа или оверлей молчит дольше 15 секунд).
  Время при `ads=0` не копится: рекламодатель не платит за минуты, когда гость заполняет форму. Старая версия клиента параметр не шлёт, и сервер считает
  как раньше (пока ПК заблокирован). Раз в 30 секунд на ПК записывается кусок не больше 60 секунд, поэтому накрутить время нельзя (`ad_stats`: клуб, баннер,
  день по времени клуба, секунды). Все баннеры очереди получают одно и то же экранное время (сервер не знает, какой из них в этот момент на экране).
  Отчёт платформы (`GET /api/platform/ads/report`): по баннерам с разбивкой по клубам и по клубам (экранное время клуба считается один раз, сколько бы
  баннеров ни шло). Баннер с записанными показами нельзя удалить, только выключить.
- **Денег система не считает.** Цену показа и расчёты с рекламодателями и клубами вы ведёте сами по часам из отчёта. Доля клуба хранится как процент.
- **Маркировка.** По закону о рекламе интернет-реклама маркируется (erid, отчётность через оператора рекламных данных). Поля `advertiser` и `erid`
  показываются на баннере, но получать erid и отчитываться должны вы вместе с рекламодателем; юридическую сторону стоит проверить у юриста.
- **Ключ платформы** даёт доступ ко всем клубам: храните его как пароль и работайте с панелью только по https.

### Меню гостя после входа и продление тарифа (сделано)

- **Раскладка.** Слева названия вкладок (ПК и клуб сверху), по центру «Библиотека» (игры плакатами, под линией программы компактными плитками; чипов
  с категориями нет, категория остаётся подписью и фильтром только в «Баре»), «Бар», «Тарифы». Справа колонка, которая видна всегда: «ОСТАЛОСЬ» крупно (или
  «ХВАТИТ БАЛАНСА НА», если время считается от баланса), тариф, баланс и кнопки.
- **Продление: `POST /api/me/sessions/extend {tariff_id}`.** Продлевать можно пакетом часов сессию, начатую с пакета или ночи. Почасовую сессию продлевает
  пополнение баланса (409 с понятной фразой), поэтому в меню для неё кнопки нет. Если оплаченное время уже кончилось и шла доплата по часам, набежавшая
  сумма сначала списывается отдельной строкой («Доплата по часам ... (перед продлением)»), потом пакет («Продление: название»), а новый пакет считается
  от этого момента: одни и те же минуты не оплачиваются дважды. Конец оплаченного времени (`base_end`) сдвигается на длину пакета, конец сессии
  (`planned_end`) пересчитывается по балансу и ставке доплаты. Если на этот ПК бронь другого гостя попадает в новое время, продлить нельзя (409
  «ПК забронирован на 19:30»). Не хватает денег: 402 «Не хватает N ₽». Всё списывается через `services/wallet.py`; сумма продлений накапливается в
  `sessions.extra_paid` и входит в итоговую стоимость сессии (`billing.compute_cost`), поэтому отчёт и закрытие сессии её не теряют.
- **Пополнение пока вызывает администратора.** Кнопка «Пополнить баланс» создаёт вызов с текстом «Пополнение баланса»: деньги гость отдаёт на стойке, как и
  раньше. Когда будет выбран платёжный провайдер (QR, онлайн), кнопка начнёт показывать оплату, остальное не изменится.
- **Время в игре.** Отдельного окна с таймером поверх игры нет (так решено раньше): продлить и посмотреть остаток можно в меню; за 15, 10 и 5 минут до конца
  приходит уведомление.

### Обложки игр (сделано)

- **Хранение.** Таблица `app_covers`: одна обложка на игру (`app_id` первичный ключ), PNG или JPEG до 2 МБ, каждая сторона от 100 до 4096 пикселей (тип и
  размеры проверяются по самим байтам, как у баннеров), `version` = отпечаток картинки, `source` = `steam` или `manual`. Вертикальный постер, лучше 600 x 900.
  Миграция 0011. Копирование каталога между клубами переносит и обложки, удаление игры удаляет обложку.
- **Два источника.** Кнопка «Подтянуть обложки из Steam» в админке (Игры): сервер сам берёт постер `library_600x900.jpg` из каталога Steam для
  игр с запуском через Steam, у которых обложки ещё нет (ПК в интернет за картинками не ходят). Не больше 60 секунд за нажатие, остальное при следующем:
  ответ говорит, сколько добавлено, не найдено и осталось. Ручная загрузка («Обложка» в строке игры) главнее: автоматика её никогда не заменяет;
  удалить ручную можно кнопкой, и тогда снова подойдёт Steam. Картинки Steam принадлежат правообладателям; в меню клуба их использование на ваше
  усмотрение, при необходимости загрузите свои.
- **Доставка на ПК.** В списке игр для агента (`GET /api/agent/apps`) у каждой игры `cover_version`; картинку служба берёт по
  `GET /api/agent/apps/{id}/cover` (ключ ПК, только активные игры своего клуба, ETag = версия). Служба проверяет тип, размер и версию, кладёт файл
  «номер-версия.расширение» в `C:\ProgramData\ClubOS\covers` (в разработке `CLUBOS_COVERS_DIR`), убирает лишнее и отдаёт оверлею только путь; через
  канал картинки не ходят. Не успело скачаться за 6 секунд: игра в списке без обложки, меню спросит ещё раз через 5 секунд. Вход гостя обложек не ждёт.
- **Вид.** Плакат 2 на 3 с названием под ним, возрастной ценз в углу, при наведении золотая рамка и белая плашка «ЗАПУСТИТЬ». Нет обложки: плитка с большой буквой
  названия. Игра не установлена на этом ПК: плитка приглушена. Программы (Steam, браузер) обложек не имеют и остаются компактными плитками.

### Порядок работ

1. ✅ **Готово.** **Меню гостя:** каталог игр (сервер + управление в админке), окно-меню в клиенте, запуск, правая колонка.
2. ✅ **Готово.** **Сервисы:** вызов администратора, бар и заказы с оплатой с баланса, раздел «Заказы» и «Бар» в админке (подробности ниже).
3. ✅ **Готово.** **Карта клуба и дашборд:** зоны и расстановка, расширенные статусы, боковая панель, отчёт железа от клиента.
4. ✅ **Готово.** **Бронирование** мест.
5. **Нужны внешние решения:** QR-оплата и онлайн-пополнение (провайдер), реальный SMS, роли сотрудников, переключатель клубов в шапке админки
   (это тот самый открытый вопрос из раздела 13: сеть клубов под одним входом требует сущности «организация»).

Достижения, рейтинг, бонусы, «активировать код друга» и избранное из референса в первую версию не входят.
